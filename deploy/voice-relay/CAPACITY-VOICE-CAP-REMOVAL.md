# Снятие лимита шести: локальный кандидат конфигурации

**В этом задании production не менялся.** В template изменено только `user-quota=20` → `512`; общий лимит **960 allocations**, **1024 UDP relay-порта**, bandwidth и ограничения процесса сохранены. Это подготовка следующего выпуска, а не подтверждение применённой настройки.

## Почему требуется изменение TURN

Один клиент получает один временный credential из `server/voice-config.ts` и передаёт его всем своим `RTCPeerConnection` в `client/voice.ts`. Поэтому coturn `user-quota` ограничивает совокупность его peer connections. При 20 allocations и 2/3/4 allocations на peer connection скрытый потолок получается приблизительно 11/7/6 участников соответственно; перекрывающиеся поколения при переподключении расходуют дополнительный запас. Число ICE candidates само по себе не является точным счётчиком allocations.

Плановый бюджет на credential: самая большая существующая комната — **64 участника**, то есть 63 peer connections; **4 allocations × 2 поколения × 63 = 504**, округлено до **512**. Четыре allocations и два поколения — явно выбранные допущения для запаса, а не гарантия поведения любого браузера/набора интерфейсов. Размер квоты не означает, что столько connections выдержит браузер.

## Фактические игровые границы

| Комната | Максимум игроков по текущему коду |
|---|---:|
| Lobby | 64 |
| Paintball | 16 |
| Fight | 16 |
| Hide | 8 |
| Skill | 5 |
| Kart / Boat / Fort | по 6 |

Границы определены в `shared/lobby.ts`, `constants.ts`, `fight.ts`, `hide.ts`, `skilltest.ts`, `kart.ts`, `boatrace.ts`, `fort.ts` и проверяются соответствующими `hasSpace()`. Сумма вместимостей — 127 игроков; отдельного общего connection cap в `Hub.connect`/WebSocket upgrade не обнаружено. Voice membership по-прежнему привязан к комнате.

Полный mesh из 64 человек создаёт **4032 конечных peer connections** (2016 пар). Все заполненные комнаты — **4678 конечных connections**. Даже один allocation на connection превышает текущие 960, если весь большой mesh требует TURN. При 2/3/4 allocations на connection отдельная полностью relayed комната теоретически заполняет пул примерно на 22/18/16 участниках; другие комнаты и старые allocations уменьшают доступный остаток. Это расчёт бюджета, не нагрузочная приёмка и не новый продуктовый лимит.

## Проверка квоты

Изолированный loopback coturn 4.18.0, отдельный свежий credential, production не использовался:

- При `user-quota=20` открылись 20 allocations; 21-й получил TURN **486 Allocation Quota Reached**.
- При `user-quota=512` одновременно открылись **96 allocations на одном credential**, ошибки квоты не было; затем все освобождены `Refresh lifetime=0`.
- Общая квота тестового relay — 960, диапазон — 1024 порта; секреты остались в приватных локальных файлах, значения/адреса peers не выводились.

Это доказывает устранение старого ограничения credential для проверенного объёма, но не заменяет native RTC проверку 8/12 клиентов. Эти браузерные проверки, общий gate и решение о следующем релизе выполняет ведущий отдельно.

Крупный mesh остаётся квадратичным по числу соединений и нагружает CPU/сеть браузеров. Полную доступность голосовой связи для 64 участников и восьми заполненных комнат здесь не обещаем. При необходимости такого масштаба следующий отдельный проект — SFU с измеренным бюджетом; незапрошенную серверную архитектуру или новые публичные порты сейчас не добавляли.
