Замечания и предложения

P1 — серьёзная надёжность/данные при указанном триггере. P2 — исправляемая логика, плавность или стоимость обработки. «По коду» подтверждает механизм; оно не означает, что величина выигрыша FPS уже измерена.

P1Q1 · НадёжностьВоспроизведено

Последний игрок уходит — крысиные бега и рулетка перестают рассчитывать ставки

RatTrack busy=true после последнего disconnect, Hub.active=false; внешний loop guard не вызывает step, escrow остаётся. Рулетка имеет такое же отсутствие в предикате; её полный сценарий отдельно не запускался.

Предлагаемый шаг. Включить оба busy в единый предикат жизнеспособности хаба и переиспользовать его в запуске/остановке цикла. Небольшой тест последнего disconnect должен идти через тот же внешний guard, что main.loop.

Причина, последствия и проверка

Единственный/последний онлайн игрок ставит на крысу либо в рулетке и полностью выходит до расчёта; остальные комнаты и активные карточные столы пусты.

Раунд и залог зависают до следующего входа; при рестарте вернётся исходная ставка вместо результата. Это не доказанная безвозвратная потеря денег, а нарушенный обещанный расчёт даже после выхода.

server/hub.ts:366–367

Hub.active includes card tables/director/billiards but excludes ratrace.busy and roulette.busy. main.loop returns when !hub.active before calling Hub.step. The narrower Hub.step guard already accounts for both betting games, so it never gets reached. Synthetic RatTrack bet20 then final Hub.disconnect yielded trackBusy=true, hubActive=false, phase=open and escrow20 after advancing wall-clock60s and applying actual main-loop active guard. Existing ratrace test helper advance() calls hub.step unconditionally, bypassing this boundary.

Приёмка. Объектный интеграционный тест RatTrack и RouletteTable: все клиенты ушли, wall-clock прошёл дедлайн, глобальный цикл продолжился, итог записан один раз и escrow очищен. Отдельно проверить остановку после завершения.

P1Q2 · НадёжностьВоспроизведено

/health считает незавершённый денежный розыгрыш безопасным для выкладки

health.busy=0 во время незавершённой ставки на крысу даже с игроком online. deploy.sh использует это поле как защиту от прерывания. Это локальный репро, не наблюдение боевого релиза.

Предлагаемый шаг. Добавить оба незавершённых розыгрыша в busy и закрепить одну явную политику незавершённых денежных операций для active/health/shutdown.

Причина, последствия и проверка

На сервере только площадь; идут крысиные ставки/забег либо рулетка, других busy режимов нет; штатная выкладка спрашивает /health.

Штатная выкладка способна прервать розыгрыш, хотя пользователь не разрешал FORCE. Startup refund protects исходную ставку, но выигрыш/результат и анимация обрываются.

server/hub.ts:1106–1113

health.busy sums mode humans, card tables, director, billiards and plane, but excludes roulette.busy/ratrace.busy. deploy.sh chooses health.busy to decide interruption safety. Offline reproduction returned healthBusy=0 during live RatTrack open phase with an online bettor and escrow20. Not merely the final-player Q1 case: release guard is wrong while bettor remains online.

Приёмка. Негативные тесты health.busy в open/run/spin и положительный idle; тест deploy gate с этим ответом. Production state не проверен.

P1Q4 · НадёжностьВоспроизведён отказ I/O

Сбой записи Store выходит неперехваченным из игрового ввода или тика

Синтетический отказ primary write: exception, tokens в памяти 80, на диске 100, escrow в памяти 20. Exception выходит из callbacks без error boundary. Падение живого процесса специально не запускалось.

Предлагаемый шаг. Прописать безопасную политику: различать primary committed / backup failed, остановить новые денежные операции при primary failure, сообщить health degraded, повторить pending save с ограничением и выполнить контролируемое завершение если запись не восстанавливается. Не добавлять blind catch, который продолжит выдавать незаписанные выигрыши.

Причина, последствия и проверка

ENOSPC/permission/I/O failure or backup-write failure during ordinary save, paid action or result tick.

Один временный сбой диска может оборвать все комнаты. Невыплаченные escrow возвратятся после старта, но до секунды отложенных наград/прогресса других игроков не гарантированы. Backup failure after primary rename also gets presented as action failure despite already committed data.

server/store.ts:357–364

Debounced timer calls flush without catch; reserve/settle methods mutate memory, call flush, and propagate its Error; main message callback and tick callback call hub without an error boundary. Synthetic primary write failure (state.json.tmp replaced by directory) produced Error, in-memory balance80/escrow20, primary balance100. No runtime rollback for escrow, unlike grantSet's primaryRevision handling (profiles.ts615–624). Ordinary Node unhandled callback exception would terminate process; reviewer did not start a live server.

Приёмка. Failure injection на reserve, settlement и debounce; отдельный отказ до rename и после primary commit. Проверить all-or-nothing баланс/escrow и управляемый operational boundary, не только Store.flush unit-test.

P2Q5 · НадёжностьЗамерено + код

Каждая ставка и выплата синхронно переписывает все профили и делает fsync в общем потоке

Настоящие Profiles.settleRat/Store: 8 выплат — медиана 38 мс / 8 записей; 32 — 158 мс / 32 записи; 64 — 334 мс / 64 записи. По три повтора, искусственные профили и локальный диск. Это не время записи на VPS.

Предлагаемый шаг. Начать с batch settlement целого RatTrack/roulette/Blackjack события одним durable snapshot по образцу Durak, сохранив reserve durability before acknowledgment. Измерить fsync/JSON p95/p99 на синтетической копии до решения о отдельном writer/journal.

Причина, последствия и проверка

Растёт число сохранённых профилей или несколько людей ставят/получают результат одновременно; день первой записи дополнительно пишет backup.

Потенциальный общий jitter в движении/командах всех режимов и лишнее disk I/O; результат одного общего события может частично сохраниться до аварии. Не доказано, что текущая небольшая компания уже упирается в это.

server/profiles.ts:543–560

Every reserve/settle flush JSON.stringify(state) + synchronous write/fsync/rename of the full profile array. RatTrack, roulette and Blackjack settle each bettor separately in one tick. N payouts therefore incur N full-state writes/fsyncs instead of one; primaryRevision increments per payout. An interruption between committed payouts leaves a partially settled event; remaining escrow refunds stake at restart. Durak already uses batch reserve/settle, proving a local existing pattern.

Приёмка. Синтетические 64/1000/10000 профилей и 1/8/32 ставки; tick/event-loop latency и число disk commits, invariant выплаты/escrow после fail injection. Writer/thread/БД не нужны без измеренного остаточного bottleneck.

P2net-01 · Сеть / плавностьВоспроизведено

Возврат в прятки теряет изменения предметов, прошедшие без связи

Независимый повтор: предмет изменился 110 → 310 см во время detach; после attach full=false, p=[], pending=0. Проверены реальные HideGame и SessionLink; полный браузерный reconnect этого сценария не запускался.

Предлагаемый шаг. Короткий room resume hook: для HidePlayer сбросить sentEpoch и отправить полный snapshot после attach. Долгосрочно — baseline generation/ack для дельт. Не добавлять слепое отбрасывание hide_state по давлению.

Причина, последствия и проверка

Сеть оборвалась, за время обрыва предмет переместился и остановился либо исчез. Hub сохраняет ту же комнату/HidePlayer, затем возвращает сокет без пересоздания сцены.

Клиент после успешного reconnect сохраняет старое место или отсутствующий предмет до следующего изменения/смены epoch. В прятках это влияет на поиск и точность выстрелов.

server/hide/game.ts:545–563

hide_state содержит дельту к p.sent, а не полный заменяемый снимок. view изменяет p.sent до вызова sink; SessionLink при detach выбрасывает volatile hide_state. В Hub.resume отсутствует reset sentEpoch/room full resync. Настоящие HideGame.send/SessionLink, hideSetup(2)/toSeek: initial full=true, prop x=110cm; detach; prop x+=200cm; send; attach; send => actual x310cm, resumed full=false,p=[], pending=0.

Приёмка. Два клиента: reconnect hunter, пока prop перемещается и останавливается; отдельно поймать prop во время обрыва. Проверить полный снимок после replay и отсутствие утечки скрытых предметов в blind phase. Offline воспроизведение сделано; браузер/runtime не запускались.

Ограничения изменения. Полный resync коротко увеличивает payload; требуется сохранить blind/role visibility, порядок replay и server-authoritative phase. Простое внесение hide_state в reliable replay увеличит трафик и не решает произвольный baseline skip.

P2net-02 · Сеть / плавностьВоспроизведено

Backpressure молча теряет одноразовый reset картинга

Независимый повтор реальных encoders и sendServerBinary: при 512 КиБ kart type3 reset не отправлен и соединение не закрыто; обычный type2 reset отправлен.

Предлагаемый шаг. Включить reset type3 в guard либо передавать transport explicit critical flag; ещё устойчивее — повторяемый reset generation до ack. Не считать повторяемый regatta reset counter одноразовым флагом.

Причина, последствия и проверка

Возврат карта на КТ/телепорт/reset в момент исходящей очереди 512KiB..1MiB.

Критический reset исчезает без fresh handshake; следующий снимок запускает обычный reconcile вместо predictor.reset/camera reset, вызывая большой сглаживаемый сдвиг и проигрывание старых вводов.

server/voice-wire.ts:43–52

Защита reset признаёт только MSG_SNAPSHOT=2. Картинг использует MSG_KART_SNAPSHOT=3 с тем же flags byte9. Сервер снимает k.selfReset до отправки. Настоящие encodeKartSnapshot/encodeSnapshot и fake socket bufferedAmount=512*1024: type3 flags3 => sent0,closed[]; type2 flags3 => sent1,closed[].

Приёмка. Тест обоих encoder типов на 512KiB и 1MiB; race return-to-checkpoint при congestion; проверка что reset отправлен или соединение явно закрыто. Offline encoder repro выполнен; симптом в браузере не измерен.

Ограничения изменения. Принудительный reconnect при reset повышает надёжность ценой разрыва гонки. Повторный reset без generation/ack может повторно сбрасывать клиент и портить плавность.

P2C1 · Сеть / плавностьВоспроизведено

Сверка катера и самолёта нарушает непрерывность картинки между тиками

Катер: поправка физики 5 см дала скачок картинки 20,3 см при alpha=0 и 10,2 см при alpha=0,5. При alpha=1 скачка нет. Аналогия самолёта установлена по коду; отдельный репро самолёта не запускался.

Предлагаемый шаг. Сохранить непрерывный интервал prev/current при сверке, как в общем Predictor, либо вычислять offset от реально показанной позы. Сброс после телепорта оставлять мгновенным. Применить одинаковый принцип к катеру и самолёту.

Причина, последствия и проверка

While moving, receive a correction for newest predicted input, e.g. server-only boat collision. The receipt occurs between simulation ticks, so render alpha is below 1. At 120 Hz alpha spans intermediate values; at 60 Hz it is also often below 1 because queue pacing adjusts tick rate by ±3%. More pending inputs can reduce or alter the jump but do not ensure continuity when replay changes velocity.

A small server correction can cause a visible position/camera jump as large as one physics step, despite correction offset smoothing; on faster plane motion the same formula can magnify the visible movement. This is a source/probe result, not a measured in-game incidence rate.

client/lobby/regattapredict.ts:77–101

accept() saves old state only, resets prev to authoritative state, replays entries and calculates offset from old current state. The render path uses lerp(prev,state,alpha)+offset (regatta.ts:514–525). When ack==newest and a small correction occurs, prev and state become identical; offset protects alpha=1 but not the displayed position for alpha<1. Pure Node reproduction: initialize RgPredictor with placeRgBoat(), velocity 12 m/s, predict seq=1, accept ack=1 with authoritative x correction +0.05 m. Measured draw discontinuity: alpha=0 => 0.20326797385620665 m; alpha=0.5 => 0.10163398692809977 m; alpha=1 => 0 m. Predicted one-tick displacement was 0.20326797385620665 m. Same algorithm in client/lobby/plane.ts:192–216 resets prev to server state and derives offset from old current state; rendering at 446–448 interpolates prev/state. General Predictor.reconcile preserves continuity by translating prev by the same position correction (client/predict.ts:149–154). Reproduction persisted as regatta-correction-repro.mjs and regatta-correction-repro.json beside this report. Rg confirmed by executing current source; Plane follows from code comparison and has not been executed.

Приёмка. Сверка с ack==newest и несколькими replay inputs; alpha 0 / 0,5 / 1; малая поправка и намеренный teleport; проверить картинку и отсутствие ложных corrections.

P2net-03 · Сеть / плавностьЗамерено + расчёт

Набережная рассылает всех игроков каждому 30 раз в секунду

64 клиента: основной браузер получил 31,3–31,8 КБ/с payload. Формула только binary: (156+14N)×30; при N=64 это 31 560 B/s каждому и 2 019 840 B/s всей комнате. Суммарный исходящий трафик комнаты здесь рассчитан, не измерен.

Предлагаемый шаг. Сначала измерить visible/near peer fraction. Сохранить self ack cadence, разделить nearby динамику и far low-rate updates; spatial interest с hysteresis, отдельными despawn и roster. 60Hz рядом выбирать после budget comparison; дальние10–15Hz, крупные global события отдельно.

Причина, последствия и проверка

Большая компания распределена по площади/пирсу/аквапарку; значительная часть чужих аватаров далеко или за камерой.

Трафик и snapshot copy/fanout растут O(N²), клиент декодирует и обновляет ненужные далёкие сущности. Удвоение всей комнаты до60Hz удвоит этот baseline.

server/lobby/room.ts:1981–2012

Локальный FIFO-прокси добавлял 40 мс на сторону (номинально +80 мс RTT), затем ±20 мс jitter на сторону. На стабильной задержке corrections оставались 0; с jitter счётчик вырос до 12, исходящий bufferedAmount оставался 0. Это короткая переходная проверка движения, не оценка плохого Wi-Fi и не тест TCP packet loss. История ClockSync сохраняется между сценариями; поэтому значения delay из этой серии нельзя выдавать за стационарную минимальную задержку.

Исходные состояния · Прокси и smoke-сценарий

WebRTC DataChannel пока не является следующим обязательным шагом. В данном исследовании нет измерения реальных потерь TCP или блокировки из-за retransmission. Сначала исправить контракты snapshot/replay и измерить очередь; менять транспорт имеет смысл только под подтверждённую проблему.

Качество кода: что сохранить и где упрощать

У проекта уже есть полезная основа: сервер решает экономику и результаты, физика разделена с клиентом, snapshots компактны, input budget защищает от ускорения, протокол версионируется, SessionLink восстанавливает важные события, мировые ресурсы кэшируются по принятому решению. Не нужно заменять эти системы общим новым фреймворком.

Две ошибки денежных режимов показывают конкретную проблему границ: списки «комната требует шага» и «релиз нельзя прерывать» поддерживаются отдельно. Нужен небольшой общий контракт для незавершённых операций, с тестом на внешний main-loop guard. Сейчас тесты отдельных игр могут вручную вызывать step и пропускать эту границу.

Для выплат уже есть образец пакетной операции в Durak. Переносить именно этот принцип в RatTrack/roulette/Blackjack полезнее, чем просто асинхронно писать файл: подтверждать деньги до durable commit нельзя. Политика I/O отказа должна различать неуспешный primary commit и проблему резервной копии.

Дополнительные риски и отложенные направления
  • Частично повреждённый валидный JSON. Синтетический primary с одним неправильным nick загрузил 1 профиль вместо 2, хотя backup содержал оба. На реальных данных такого состояния не наблюдали. Политику quarantine/recovery стоит закрепить отдельно, без ломания допустимых миграций.
  • Коллизии. Линейные обходы CollisionWorld подтверждены кодом. Профиль площади не показал их главным расходом. Spatial broad phase — только после отдельного замера и с сохранением детерминированного порядка.
  • Бильярд. Один удар действительно рассчитывается синхронно, но локальные микрозамеры дали медиану 2,4–4,1 мс и p95 до 8,6 мс. Это не доказательство необходимости worker сейчас; нагрузку нескольких столов на VPS ещё не измеряли.
  • WebGL context restore. Повторное построение процедурных PMREM по коду явно не предусмотрено. Видимый дефект после потери context не воспроизводили; этот пункт остаётся гипотезой, а не подтверждённой поломкой.

Независимая проверка методологии и архивов

Предлагаемый порядок работ

Деньги и reconnect — первый небольшой патч

Q1/Q2: единая политика active/busy для незавершённых розыгрышей. Net‑01/02: полный resync Hide и защита kart reset. C1: сохранить непрерывность prev/current при reconciliation. Приёмка: последний disconnect, занятый релизный health, reconnect двух игроков, congested socket и alpha 0/0,5/1.

Убрать серверные остановки на выплатах

Q5/Q4: атомарная выплата всего раунда одним durable snapshot по существующему образцу; явная политика primary I/O failure. Цель — заменить N полных записей на одну и измерить p95 event-loop pause. Не подтверждать деньги до сохранения.

Сделать низкое качество полезным для CPU

R2–R6: обратный подъём с hysteresis, исключить переходы из решения auto, передавать effective tier всем эффектам, стабилизировать набор ламп, упростить дальние детали аватаров. R8 — отдельный компактный шаг по крысам. Приёмка: одинаковые виды 1/16/64, 1080p/4K/CPU×4 и сохранение стиля.

Батчинг — вместе с перестройкой площади

Продолжить существующий kit: статику по материалам и зонам, повторяемое инстансами, общую палитру. Не латать всю старую площадь заранее и не трогать защищённые объекты. Цели из действующего плана: ≤300 calls, ≤80 программ начальной площади, ≤3 мс CPU на M1 Pro.

Сеть — по измеренной свежести

Инструментировать queue age/drop, jitter, corrections и видимый возраст чужих. Затем versioned roster Skill, общая сериализация broadcast, разделение pirate motion/loot, near/far interest без нарушения self ack и liveness. Частоты и транспорт менять после сравнения того же сценария.

Это предложения к реализации, не выполненные изменения. Не обещаем заранее ×2 FPS или конкретный процент трафика: для каждого шага нужен один сопоставимый замер до/после. Сохранены решения владельца: не дробить загрузку и не выгружать миры ради мегабайтов; не покупать мощнее сервер без измеренной причины.
