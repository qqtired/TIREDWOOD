# Голосовой чат Game Opus: реализуемость

Позднее в тот же день владелец разрешил реализацию. Актуальный локальный MVP и границы проверки — [voice-mvp.md](../voice-mvp.md). Ниже сохранено исходное исследование до реализации; утверждение «код не менялся» относится к этому этапу.

**Рекомендация:** сделать desktop push-to-talk через WebRTC + Opus, начать с голосовой группы до 6 человек, добавить собственный TURN. Для общей набережной/режимов на 16–64 человека — отдельный SFU. Сжатие выполняет браузер; OpenAI TTS, ключи API и платная речевая служба для этого не нужны.

Предположение: «TTS/touch to speak, чтобы мы в игре разговаривали» означает живой голос с удержанием клавиши. Это исследование от 2026-10-03: голосовой код и инфраструктура не менялись, сервер/SSH/рабочие данные не открывались. Оценки ниже — расчётные допущения, не измерения сети игроков.

## MVP для пользователя

1. Отдельная кнопка «Включить голос»: понятный запрос микрофона и запуск воспроизведения по пользовательскому действию. До разрешения — микрофон выключен. `getUserMedia` требует разрешения и безопасного контекста; Chrome также ограничивает autoplay. [Mozilla: getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), [Chrome autoplay](https://developer.chrome.com/blog/autoplay/).
2. Удерживать `V` (в обследованных основных обработчиках свободна): индикатор «Говорите», отпускание мгновенно закрывает передачу речи. Изначально `track.enabled=false`; только после готовности канала разрешать PTT. Выключенная дорожка даёт тишину, но не гарантирует нулевой сетевой трафик; браузер может временно освободить устройство. Не запрашивать разрешение и не пересоздавать соединение при каждом нажатии. Полное «Выключить голос» останавливает track и закрывает соединения. [W3C Media Capture](https://www.w3.org/TR/mediacapture-streams/#dom-mediastreamtrack-enabled).
3. На `keyup`, blur, скрытие вкладки, потерю связи, открытие меню/чата и смену комнаты — немедленный stop. На телефоне позднее та же модель через удержание кнопки и `pointercancel`; desktop первым.
4. Видно, кто говорит; есть выключение своего микрофона, общего прослушивания, отдельного собеседника и громкость голоса. Не совмещать смысл выключения динамиков с разрешением микрофона. Никакой фоновой записи или транскрипции.
5. Первый объём — канал сидящих за одним карточным столом и/или группа крепости/гонки до 6 человек. Смена комнаты разрывает канал. Общее «все слышат всех» для набережной не включать. Пространственную громкость/соседей добавить отдельным этапом после проверки сети.

Канал — серверное правило доступа, а не только уменьшенная громкость: нельзя передавать звук всем и считать дальних «защищёнными» клиентским mute. В mesh строгий отзыв доступа у модифицированных клиентов ограничен: уже соединённые недобросовестные peers могут игнорировать закрытие. Для серверно управляемых подписок/блокировок и общей proximity-системы предпочтителен SFU.

## Аудиотракт и «пережать быстро»

`микрофон → обработка браузера → Opus → DTLS-SRTP/ICE → peer или SFU → jitter buffer → динамики`.

Opus обязателен для WebRTC endpoints. Запросить mono, echoCancellation/noiseSuppression/autoGainControl как предпочтения, проверить фактические capabilities/settings. Начальная цель — **32 кбит/с**, пакеты около **20 мс**; при плохой сети пробовать 24 кбит/с. Не делать WAV/MP3, MediaRecorder-чанки или собственный кодек. [RFC 7874](https://www.rfc-editor.org/rfc/rfc7874.html), [RFC 7587](https://www.rfc-editor.org/rfc/rfc7587.html).

Битрейт задавать поддерживаемым `RTCRtpSender.setParameters()`; `maxBitrate` не включает транспортные заголовки. Opus ptime/DTX/FEC — параметры согласования, а не гарантированная одинаковая ручка во всех браузерах: проверить negotiated SDP и `getStats`, не обещать жёсткие 20 мс/нулевой трафик в тишине. Browser congestion control оставить включённым. [W3C WebRTC](https://www.w3.org/TR/webrtc/#dom-rtcrtpencodingparameters-maxbitrate).

**Расчёт, не benchmark:** 32 кбит/с = 80 байт полезного аудио за 20 мс. Если заложить условные 60 байт RTP/UDP/IP/SRTP/extensions на пакет, 50 пакетов/с дают ещё 24 кбит/с. Для бюджета округлить один активный направленный поток до **64 кбит/с ≈ 28,8 MB/час**; это запас, реальность зависит от IPv4/IPv6, расширений, RTCP, TURN и тишины. Один только кодек: 14,4 MB/час. DTX/PTT обычно уменьшают средний расход, но считать по измеренным данным.

| Одновременные участники | Mesh: копий своего потока | Upload одного говорящего при 64 кбит/с на копию | Соединений между всеми peers |
|---:|---:|---:|---:|
| 2 | 1 | 64 кбит/с | 1 |
| 6 | 5 | 320 кбит/с | 15 |
| 16 | 15 | 960 кбит/с | 120 |
| 64 | 63 | 4,03 Мбит/с | 2016 |

**Порог — инженерная рекомендация, не лимит стандарта:** mesh до 6; уже для 8+ и устойчивой общей комнаты предпочесть SFU. SFU принимает одну копию голоса и пересылает выбранным слушателям, не требует повторного кодирования в обычном сценарии. mediasoup — подходящий self-hosted вариант с Node API и отдельными C++ media workers; решение о нём принимать после выбора общего/группового голоса. [mediasoup architecture](https://mediasoup.org/documentation/v3/mediasoup/design/).

При SFU и одном говорящем на 64 человек: upload говорящего около 64 кбит/с, egress SFU около 4,03 Мбит/с. Если все 64 говорят всем одновременно — около 258 Мбит/с egress; поэтому нужны ограниченные подписки/активные говорящие. Это расчёт без накладных расходов сверх принятого бюджета, а не заявленная ёмкость текущего сервера.

Для уже установленной связи пример бюджета mouth-to-ear: пакетизация 20 мс + обработка 5–15 + сеть в одну сторону 20–60 + jitter buffer 20–60 + воспроизведение 5–15 = **70–170 мс**. Цель приёмки: p95 до 200 мс на согласованных нормальных сетях, без гарантии для любой страны/VPN. Первое включение и ICE setup измерять отдельно. Не ждать ответного WS-подтверждения на каждое нажатие PTT; перестройка peer-связей должна происходить заранее.

## Node WS, TURN и SFU — разные обязанности

| Компонент | Что потребуется |
|---|---|
| Текущий Node/WS | Join/leave, адресные offer/answer/ICE, server-issued session/channel generation, авторизация адресата по текущим Client/room; лимиты размеров/частоты; краткоживущие TURN credentials. Не принимать `from`/room со слов клиента |
| TURN | Собственный публично доступный relay, сертификат, UDP listener и диапазон relay-портов, TCP/TLS fallback; временные credentials, лимиты аллокаций и трафика. Это новое конфигурирование хоста/сети |
| SFU, если выбран общий голос | Отдельный media process/service, публичные ICE endpoints, доступные порты, авторизация produce/consume и отзыв подписок, метрики, бюджет CPU/egress; HTTP reverse proxy этого не заменяет |

STUN не гарантирует связь через NAT/firewall. TURN нужен как fallback для реальных внешних сетей; он пересылает шифрованный поток и **не устраняет mesh-дублирование**. WebRTC требует поддержки TURN/TCP и TURN/TLS для блокирующих UDP сетей. Если нужен TLS на 443, учесть занятость порта текущим HTTPS: отдельный IP/узел или продуманная L4-схема, не обычный nginx HTTP location. [WebRTC TURN guide](https://webrtc.org/getting-started/turn-server), [RFC 8835](https://www.rfc-editor.org/rfc/rfc8835.html#section-3.4).

coturn поддерживает временную secret-based авторизацию. Секрет остаётся на сервере; браузеру выдаётся короткоживущая пара. Открытый relay и долгоживущий пароль в bundle недопустимы. При прямом P2P собеседники могут узнать сетевой адрес друг друга; relay-only повышает приватность ценой TURN-трафика. [coturn](https://github.com/coturn/coturn), [W3C WebRTC](https://www.w3.org/TR/webrtc/).

CSP: оставить собственный signaling на текущем origin; только если реально появятся внешние endpoints, добавить точные разрешённые origins. Для выбранного способа воспроизведения проверить `srcObject`/WebAudio и CSP во всех целевых браузерах; не добавлять wildcard/blob-политики «на всякий случай». Явная `Permissions-Policy: microphone=(self)` подходит приложению без embed, но требует изменения deploy-конфига. Фактические production headers здесь не проверены.
