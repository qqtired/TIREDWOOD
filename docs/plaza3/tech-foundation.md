После коммита удаления номера строк в `client/lobby/scene.ts`, `client/app.ts`, `client/lobby/plaza/*` могут сдвинуться —
перед правкой ищи по имени.

PL=`client/lobby/plaza/`, P2=`shared/plaza2.ts`. Оси: x — восток, z — юг, север = −Z, `yaw = 0` смотрит на −Z.

## 0. Решение в одном абзаце

Раскладка набережной выбирается **один раз, до вычисления любых модулей с координатами**: на сервере — из
`process.env.PLAZA3` (только явная `1`, как `FISH2`), в браузере — из `globalThis.__opusPlaza`, который крошечный
`client/main.ts` ставит по ответу `/health` **до** `import('./startup-game.ts')`. Новый модуль без импортов
`shared/layout.ts` отдаёт `PLAZA3`. Каждая позиционная константа в `shared/*.ts` получает короткое подключение «на месте»:
`export const X = PLAZA3 ? <plaza3> : <старый литерал без изменений>`. Значения plaza3 — либо новые абсолютные точки
из сгенерированного `shared/plaza3/layout.ts` (входы, вывески, жители), либо **жёсткий перенос старой сборки** режима
(`xf(группа, старое значение)`: сдвиг; поворот на 90° — только где оговорено). `buildLobby()` остаётся одной функцией,
поэтому **порядок и смысл точек 0–112 одинаковы в обеих раскладках автоматически**; старые статические блоки
(павильоны, парапеты, стены) обёрнуты в `if (!PLAZA3)`, новая статика и новые точки (аркада и т. п.) дописываются
в конец. Вся новая графика — в `client/lobby/plaza3/*` (GLB павильонов, атлас вывесок, жители одной сеткой),
подключается двумя короткими ветками в `world.ts` и `scene.ts`. Без флага код идёт по старым веткам с теми же
литералами — это закрепляет тест-«отпечаток» старой карты (WP0). Протокол не меняется (новое поле `lay` в `me` —
JSON без смены номера); `PROTOCOL_VERSION` поднимет ведущий при слиянии, только если аркада добавит новые сообщения.

## 1. Рекомендуемый подход в деталях

### 1.1 Переключатель `shared/layout.ts` (новый файл, без импортов)

```ts
// Раскладка набережной: 2 — как сейчас, 3 — новая (флаг сервера PLAZA3=1). Выбирается при загрузке модуля и больше
// не меняется: сервер — из окружения, браузер — из globalThis.__opusPlaza (ставит client/main.ts до import() игры).
type G = { __opusPlaza?: unknown; process?: { env?: Record<string, string | undefined> } };
const g = globalThis as G;
export const LAYOUT: 2 | 3 = g.__opusPlaza === 3 || g.process?.env?.PLAZA3 === '1' ? 3 : 2;
export const PLAZA3 = LAYOUT === 3;
/** Значение по раскладке; plaza3 считается лениво — в старой раскладке его код вообще не выполняется */
export function pick<T>(old: T, p3: () => T): T { return PLAZA3 ? p3() : old; }
```

- **Сервер.** `server/main.ts` статически импортирует хаб → комнату → `shared/maps/lobby.ts` → все модули
  с координатами; ESM вычисляет их **до** тела `main.ts`. Окружение процесса к этому моменту уже есть, поэтому чтение
  `process.env` внутри `shared/layout.ts` даёт верный ответ без отдельного загрузчика. В `server/main.ts` — одна строка
  в лог (`PLAZA3: новая набережная`), рядом с другими флагами (`:99-130`).
- **Только явная `1`, и в `npm run dev` тоже** (как `FISH2`, `server/main.ts:74`). Иначе у всех остальных веток и
  worktree в `npm run dev` поменяется площадь. Отступление от AGENTS §8 «без переменной — вкл. в dev» оправдано тем же,
  чем у `FISH2`; записать в README/флаги.
- **Тесты.** `node --test "test/*.test.ts"` запускает каждый файл отдельным процессом, поэтому раскладка в процессе
  одна. Старые тесты идут без переменной (= старая площадь). Тесты plaza3 начинаются с `process.env.PLAZA3 = '1'`
  и **динамически** импортируют код (`const { buildLobby } = await import('../shared/maps/lobby.ts')`) —
  статический импорт вычислился бы раньше присвоения. `npm test` с выставленной в оболочке `PLAZA3=1` сломает старые
  тесты: тест-отпечаток (WP0) первым делом проверяет `LAYOUT === 2` и пишет понятную причину.

### 1.2 Как клиент узнаёт раскладку до сборки сцены

Сейчас клиент узнаёт флаги **только из сообщений сервера** — полей приветствия `lobby` (RM:656-669: `skill`, `fort`,
`fish2`, `isle`, `roulette`, `ratrace`, `plane`, `dg`, `regatta`, `hide`, `farm`) и последующих (`juke`, `bl`, `ob`, `isle`).
Сцена набережной при этом **уже построена**: `App` создаёт `LobbyScene` в конструкторе (`client/app.ts:270`), а тот —
`LobbyWorld` с `buildLobby()` (WD:188), до соединения (экран загрузки «Собираем набережную…», `client/startup.ts`).
Режимы за флагами поэтому строятся всегда и потом прячутся/включаются (SC:408-411, 707-717, 888-951). Для раскладки
так нельзя — она должна быть известна **до** вычисления модулей.

Удобная точка уже есть: `client/main.ts` (20 строк) импортирует только `errors.ts` (тип), `identity.ts`, `startup.ts`
и грузит игру **динамически** (`load: () => import('./startup-game.ts')`). Подключение:

1. `client/main.ts` → `load: async () => { await bootLayout(); return import('./startup-game.ts'); }`, где
   `client/layout-boot.ts` (новый, без импортов из `shared/`):
   - `fetch('/health', { cache: 'no-store' })` с тайм-аутом ~1,5 с; ответ `{…, plaza: 3}` (новое поле в `hub.health()`,
     `server/hub.ts:1144`);
   - запасной путь — последнее известное значение в `localStorage['opus.plaza']`, иначе 2;
   - `globalThis.__opusPlaza = n` и запомнить в `localStorage`.
   `/health` в бою проксируется nginx на сервер (`deploy/game.nginx.conf: location = /health`), в разработке его
   отвечает сервер до Vite (`server/main.ts:203`), CSP `connect-src 'self'` его пропускает — **правок nginx не нужно**.
   Запрос идёт, пока HTML-экран загрузки рисуется (`paint()` ждёт два кадра), задержка — один короткий запрос.
2. Сверка после входа: сервер кладёт `lay: 3|2` в сообщение `me` (рядом с `build`, `isle`; `client/app.ts:761-770`
   уже перезагружает страницу при смене `build`). Не совпало (сервер перезапущен с другим флагом, `/health` не ответил) —
   записать верное значение в `localStorage` и `location.reload()` один раз (защита от петли — как `VRELOAD`,
   `client/app.ts:886-901`). Новое необязательное поле JSON — без смены `PROTOCOL_VERSION` (AGENTS §8).
3. Сервер остаётся главным: столкновения и точки он считает сам. Клиент с «чужой» раскладкой только дёргался бы
   от поправок предсказания до перезагрузки — вреда данным нет.

**Риск порядка вычисления на клиенте.** Если какой-то модуль с координатами окажется в статическом графе
`client/main.ts`, он вычислится до `bootLayout()`. Защита: (а) `main.ts` не импортирует ничего из `shared/` (кроме
`import type`); (б) тест WP0 обходит статические `import` от `client/main.ts` по исходникам и падает, если дошёл до
`shared/layout.ts`; (в) один раз после `npm run build` проверить, что `__opusPlaza` во входном чанке только
присваивается. Rolldown не исполняет модули динамического чанка раньше `import()`, так что (б) достаточно.
Прочие входы — `?dress`, `lab/`, `tools/render-bench` — остаются на старой раскладке (глобал не ставится), это нормально.

### 1.3 Данные plaza3: один источник для левел-дизайнера

По образцу фермы (`docs/farm/level/layout.json` → `tools/farm/layout.mjs` → сгенерированный `shared/farmlayout.ts`):

- `docs/plaza3/level/layout.json` — пишет левел-дизайнер (можно выгружать из Blender скриптом: пустышки
  `ANCHOR_<группа>`, `USE_<kind>_<arg>`, `SIGN_<id>`, `NPC_<id>`, боксы `COL_<id>`), с пояснениями для людей;
- `docs/plaza3/level/check.mjs` — проверки до кода: точки на настиле и не в стене, круги свободны, от центра до входа
  ≤ 50 м (5–6 с бега при 8,4 м/с), проходы ≥ 2 м, боксы не пересекаются, всё внутри ±128 м по высоте снимка;
- `tools/plaza3/layout.mjs` → `shared/plaza3/layout.ts` (`export const P3 = {…} as const`, «руками не править»).

Что в нём лежит:

### 1.4 Перенос сборок режимов: `shared/plaza3/xf.ts`

Сборка режима (стол + стулья, понтон крыс, помост колеса, полоса аквапарка) переносится **целиком**: в plaza3 её старые
литералы пропускаются через жёсткое преобразование группы. Внутренние связи (стул на `CHAIR_R` от стола, загон вокруг
настила, табло у бортика) сохраняются сами, и левел-дизайнеру не нужно перебивать сотни чисел.

```ts
// Xf = { dx, dz, rot: 0|1|2|3 } — поворот на rot·90° вокруг старого центра группы, затем сдвиг.
export const A = PLAZA3 ? P3.anchors : NONE;            // NONE[группа] === null
xfP(A.rat, {x, z}) · xfSpot(A.rat, {x, z, yaw}) · xfBox2(A.rat, {x0,z0,x1,z1}) · xfMinMax(A.rat, min, max) · xfYaw(A.rat, yaw)
```

- В старой раскладке `A.<группа> === null` → функции **возвращают тот же объект** (не копию и не пересчёт): значения
  совпадают побитно, отпечаток не меняется.
- **Сдвиг (`rot: 0`) — по умолчанию.** Работает для любой формы, где поля `x*`/`z*` — абсолютные координаты.
- **Поворот на 90°/180°** — дорогая опция для отдельных групп. Столкновения у нас — только AABB (`shared/world.ts:36-60`),
  поэтому годятся лишь четверти оборота (полуразмеры `hx/hz` меняются местами), а потребители «одномерных» констант
  (`MACHINE_XS`+`MACHINE_FRONT_Z`, `TABLE_X`+`TABLE_ZS`, `BENCH_XS`+`BENCH_Z`, `AQUA_NEAR_X`, `BOAT_DOCK_Z`) и клиентские
  модели с зашитой ориентацией придётся переписать. Цена по группам — в §3.
- Совсем новые вещи (павильоны, вывески, жители, аркада) ставятся абсолютно, с любым `yaw` (визуал), а их твёрдое —
  AABB в `colliders[]`.

### 1.5 `buildLobby()`: один порядок точек, две статики

Функция LB:205-616 остаётся одной. Изменения — короткие:

1. Литералы прямо в теле, которые зависят от площади, выносятся в объект `const L2 = {…}` (тот же модуль, значения
   перенесены как есть) и выбираются `const L = PLAZA3 ? P3_LOBBY : L2`: точки `pb_gate (0,−15.2)` LB:264, `kiosk`/зеркало
   LB:268-270, доска почёта и `recent` LB:273-275/326, `kboard` LB:303, фонари LB:287, кнехты LB:312-313, мостки и маяк
   LB:316-320, помост и оградка колеса LB:377-389 (литералы вокруг `WHEEL`), спавны, `lighthouse`, `zones`, `bounds`
   LB:567-599.
2. Старые статические блоки — в `if (!PLAZA3) { … }`: настил и бортики LB:214-221, невидимые стены LB:225-228, павильон
   автоматов (стены, крыша, столбы) LB:231-235, склад LB:244-247, гараж LB:250, заборы, ящики, бочки LB:253-262, ларёк
   LB:268, доска почёта LB:274, домик кафе LB:278, «бухта» пирса LB:481-484 (если пирс переносится). **Вызовы `add(...)`
   под `if` не попадают никогда** — только боксы (в LB:236-241 стены павильона и автоматы с их точками идут вперемешку —
   разделяются построчно).
3. `if (PLAZA3) plaza3Static(b)` (новый `shared/plaza3/map.ts`) — настил, парапеты, стены, павильоны из `P3.colliders`.
   Место вызова — сразу после старой статики, до сборок режимов (индексы боксов — внутреннее дело каждой сборки:
   `boatBoxes`, `aquaMovers`, `ratBoxes`… записываются как `b.boxes.length` в момент добавления и по сети не ходят).
4. Новые точки plaza3 (аркада, разговор с жителями, если понадобится, выход на ферму-зону) — `plaza3Interacts(add)`
   **после** последней точки `farm` (№112): №113 и дальше. В старой раскладке их просто нет, массив короче — это
   допустимо (номера 0–112 те же).
5. Точка, которой в plaza3 нет, становится пустышкой по образцу Fight Club (`add('retired', …, r = 0, label '')`,
   LB:397 в рабочем дереве): лежит на свободном настиле, сервер и клиент её пропускают (RM:1031, SC `hintNearest` ~2887).

Итог: **номера и смысл (`kind`, `arg`) точек 0–112 совпадают в обеих раскладках по построению**, меняются только
`x, z, yaw, r`. Это закрепляет тест plaza3 против зафиксированного списка `kind/arg` (фикстура из WP0).

### 1.8 Протокол и номера точек

- Раскладка протокол не меняет: снимки — `x,z` int24/256 (±32 км), `y` int16/256 (±128 м) (`shared/protocol.ts:89,134-136`),
  площадь 100×75 м укладывается. Номера боксов по сети не ходят (`shared/messages.ts` — нет), номера точек — ходят
  (`use`, RM ~944), поэтому §1.5.
- `lay` в `me` и `plaza` в `/health` — новые необязательные поля JSON, номер протокола не трогаем.
- Новые сообщения аркады (`arcade*`) — смена формата → `PROTOCOL_VERSION` поднимает ведущий при слиянии (AGENTS §4).
  Новые `InteractKind` (`'arcade'`) — короткая правка типа в LB:41.

### 1.10 Как работать параллельно, не трогая одни файлы

- Общие файлы (`shared/maps/lobby.ts`, `client/lobby/world.ts`, `client/lobby/scene.ts`, `client/main.ts`, `server/hub.ts`,
  `server/lobby/room.ts`, `shared/messages.ts`) правит **только ведущий** в WP0 (каркас веток и пустые точки подключения)
  и в конце (подключение аркады, протокол).
- Каждый помощник владеет **своими** `shared/<режим>.ts` (одна-три строки `pick/xf` на константу) и своими клиентскими
  модулями режима — пересечений между режимами нет. Литералы plaza3 — только в `docs/plaza3/level/layout.json`,
  которым владеет левел-дизайнер; помощники его не правят, а просят.
- Новое (`client/lobby/plaza3/*`, `shared/plaza3/*`, `server/lobby/arcade.ts`, `test/plaza3-*.test.ts`) — новые файлы
  у одного владельца каждый.
- Пока левел-дизайн не готов, `anchors` всех групп = `{dx:0,dz:0,rot:0}` и `points` = старые точки: **с `PLAZA3=1` игра
  сначала совпадает со старой**, и каждый пакет можно включать и проверять по одному.

## 3. Инвентарь: что меняется, если входы переезжают

Цена переноса (для левел-дизайнера и заданий):
**0** — остаётся на месте, если сохранить береговые линии (§7); **Н** — новая абсолютная точка из `layout.json`
(0,5–1 ч на вход, визуал входа — новый павильон); **С** — сдвиг сборки через `xf` (1–3 ч с клиентскими литералами);
**П** — поворот сборки на 90°/180° (0,5–1 день: одномерные константы, зашитая ориентация моделей, AABB);
**Р** — переписать данные/маршруты (0,5–1 день).

Сервер во всех случаях проверяет E по расстоянию `hypot ≤ r + 0,5` и `|dy| < 2` от точки `map.interact[id]`
(`onUse`, RM:923-932) — поэтому точки должны совпадать с тем, где игрок реально стоит; столкновения — из `map.boxes`.

### 3.4 Что считается при загрузке модулей (почему выбор — до импорта)

`AQUA_FINISH`, `aquadyn.ts:165`, маршрут катера (`boat.ts:95 buildPath()`), пути парома (`ferry.ts:223-231`),
полётные скрипты гидроплана (`plane.ts:229,297,604` — прогоняют полёт целиком), `PIRATE_LOOT_HOME`/`PIRATE_ROUTES`,
`YARD_SOLIDS`/`DUNGEON_SOLIDS`, `FARM_PLAZA_GATE` и таблицы фермы, на клиенте — `billiards3d.ts:57-60`,
`ratrace3d.ts:57-63`, `ratraceboard.ts:31-32`, `photo.ts:21-23`, `plaza/aqua.ts:23`, `krakentiming.ts:8`. Ничего не
заморожено, но **«подменить объект после импорта» не сработает** — производные останутся старыми, а числа-примитивы
(`MACHINE_FRONT_Z`, `TABLE_X`, `AQUA_NEAR_X`, `BOAT_FLOOR_Y`…) вообще не подменить. Поэтому раскладка выбирается до
вычисления этих модулей (§1.1–1.2), и тогда все производные правильные сами. Сервер к тому же статически импортирует
`shared/jukebox.ts` и `shared/plane.ts` прямо из `server/main.ts:23-24` — чтение `process.env` внутри `shared/layout.ts`
это переживает.

## 4. Варианты переключения и сравнение

Оценка для команды «ведущий + 4–6 помощников»; «усилие» — без арта (павильоны, жители) и без мини-игр аркады,
только переключение раскладки и перенос режимов.

| | (a) Один объект `layout`, все позиции в нём | (b) Якоря у каждого режима (локальные координаты + якорь) | (c) Отдельная карта `lobby3` и свой `buildLobby3` | **(d) Рекомендую: выбор на месте + перенос групп + новая статика в новых файлах** |
|---|---|---|---|---|
| Суть | Все ~300 литералов из ~30 модулей переезжают в `shared/layout/{plaza2,plaza3}.ts`, модули читают `L.xxx` | Каждый режим переписывается в локальные координаты, мировое положение = якорь∘локальное | Новый файл карты с копией порядка точек; режимы параметризуются якорями | Старые литералы остаются на месте; рядом `PLAZA3 ? …`; сборки режимов в plaza3 переносятся `xf()`; статика — `if (!PLAZA3)` + `plaza3Static` |
| Усилие | Высокое: 2–3 дня только перенос литералов, + клиентские литералы | Очень высокое: переписать ~20 режимов и их 3D (≈1–2 нед.) | Высокое: копия LB ~400 строк + якоря в режимах (как b) | **Среднее: WP0 ≈ 0,5–1 день ведущего; перенос режимов ≈ 0,5–2 ч на группу** |
| Риск для старой площади | Средний: опечатка при переносе (ловит отпечаток), огромный дифф в общих файлах | Высокий: пересчёт через якорь меняет числа на 1e-15 → «ровно как раньше» уже не доказать отпечатком | Низкий для старой, но **две копии** LB расходятся: каждая будущая правка рыбалки/острова в LB забудется в `lobby3` | **Низкий: старые литералы не тронуты; `xf(null, v)` возвращает тот же объект; отпечаток доказывает** |
| Дублирование | Двойной набор всех чисел, даже того, что не двигается (море, остров) | Нет | Весь порядок точек и боксов режимов | Только то, что реально меняется |
| Тесты | Старые без правок; новые — env | Старые надо переписывать | Старые без правок; новые — env | **Старые без правок; новые — env + динамический импорт; отпечаток + фикстура kind/arg** |
| Номера точек | Сохраняются (один `buildLobby`) | Сохраняются | Надо поддерживать руками + тест сверки | **Сохраняются по построению** |
| Протокол | Без изменений | Без изменений | Если делать новую комнату — меняется `RoomKind` (чат, голос, переходы, `scene`) | **Без изменений (`lay` — новое поле JSON)** |
| Параллельная работа | Плохо: все правят один большой `layout`-файл | Хорошо по режимам, но долго | Плохо: все правят `lobby3.ts` | **Хорошо: свой `shared/<режим>.ts` у каждого; числа plaza3 — у левел-дизайнера** |
| Долгий срок | Чисто | Чище всего | Две карты навсегда | После выпуска plaza3 старые ветки удаляются одним коммитом (отпечаток и `if (!PLAZA3)` уходят) |

Почему не новая комната/`RoomKind` для (c): `'lobby'` зашит в переходы (`scene`), чат по комнатам, голос, `circlechat`,
`readygate`, возвраты из режимов (RM: выбор спавна по `from`), `/health`. Ничего из этого раскладке не нужно — одна комната,
другая карта.

Что взято из (b): **якорь + локальные координаты** уже есть у калитки фермы (`shared/farmlayout.ts` → `plazaGate.anchor`
(29,8; −12; yaw −π/2) + `local` + готовый `current`) и у входа «Подземелья» (`DUNGEON_ROCK.yaw`, P2). Для них plaza3 —
просто новый якорь. Остальные режимы получают «внешний» перенос `xf()` без переписывания внутренностей.

## 5. Отрисовка и производительность plaza3

### 5.1 Бюджет и откуда сейчас перебор

Бюджет (`docs/optimization.md:92-97`): в любой точке и при любом взгляде **≤300 отрисовок вместе с тенями, ≤80
программ шейдеров, ≤1,2 млн треугольников, процессор ≤3 мс/кадр на M1 Pro, при процессоре ×4 ≥40 FPS, вход без
замирания дольше 1,5 с**. Замер 10.10: 339–870 отрисовок, 251 программа.

Факты, на которые опирается план:
- **Тени уже статические**: `shadowMap.autoUpdate = false`, пересчёт `refreshShadows()` по событию
  (`client/render/renderer.ts:51-52,155`, ~20 вызовов из SC). Счётчик `gl.info` сбрасывается раз в кадр вручную
  (`renderer.ts:54,74`), поэтому в кадр пересчёта в `calls` попадает и проход теней — меряем и такие кадры.
- `__opus.info()` (`client/app.ts:494-496`) отдаёт `calls, triangles`, `cpuMs`, `gpuMs`, медиану/p95 кадра и память,
  **но не число программ** — его сейчас читают как `__opus.app.renderer.gl.info.programs.length`.
- **Первый вход на площадь идёт без прогрева шейдеров** (`transition.instant()`, `client/app.ts:690-692`; прогрев
  `compileAsync` есть только при смене комнат, `client/ui/transition.ts:473-494`) — отсюда замирание при входе.
- **Лампы гасятся `visible`** (WD:1273 качество, WD:1312 гроза) — меняется ключ шейдера, программы пересобираются в игре.
- Аватар ≈ 10 отрисовок (тело, глаза, веки, шапка/аксессуар, варежки, ткань, табличка-спрайт, тень;
  `client/render/avatar.ts:556-663`); 9 зазывал plaza2 — полные аватары (≈100 отрисовок по замеру редизайна).
- Склейки уже есть: `client/render/kit.ts` (`parts/addBox/buildGeo`, `paint`, `mergeColored`, `staticMesh`),
  PL/`gfx.ts` (`Mesher`, `Bulbs` одним `Points`, `Plaques` атласом), `client/farm/models.ts` (`StaticBatch` по материалу
  :137-167, `PartInstances` :172-215, общие материалы по имени семейства :30-60). `THREE.Layers` не используются,
  LOD нет, дальность — вручную по модулям (зазывалы 46 м, звери 80 м, баркас 75 м, остров 520/1300 м).

### 5.3 Материалы и программы (цель ≤80, статика plaza3 — ≤8)

- **Семейства материалов статики plaza3** (по имени материала в GLB, подмена при загрузке — как `sharedMaterial`
  в `client/farm/models.ts:32-60`):
  `p3_matte` (MeshStandard, `vertexColors`, шероховатость 0,85 — штукатурка, черепица, дерево, камень),
  `p3_gloss` (то же, 0,35 — эмаль вывесок, лак, металл), `p3_atlas` (MeshStandard + общая карта-атлас ×
  цвет вершин — плитка, полоски маркиз, ставни, мозаика), `p3_glass` (прозрачное, без записи глубины),
  `p3_glow` (MeshBasic, `vertexColors` — лампочки, окна, неон-ободки без неона), `p3_ground` (настил: карта +
  запечённые тени/AO, как сейчас WD:507-550 и `lookbake.ts`). Цвет — в вершинах, а не новым материалом.
- Один и тот же набор `defines` у всех: одинаковые `side`, `fog`, `flatShading`, без `onBeforeCompile` у статики (кроме
  ветра кипарисов — одно семейство `p3_foliage`). Программа = тип материала × defines × тени × туман, а не × объект.
- Лампы: **не больше двух настоящих** (`docs/optimization.md:109-113`), гасить `intensity = 0`, никогда `visible`.
- Прогрев: `renderer.compileAsync(scene, camera)` по сцене plaza3 на экране загрузки (этап «Собираем набережную…»),
  вместе с материалами событий (шторм, пираты) — закрывает пункт 2 этапа 1 оптимизации.
- WP-PERF добавляет в `__opus.info()` поле `programs` и команду `__opus.programs()` — перечень программ, сгруппированный
  по `name`/`cacheKey` (видно, кто плодит варианты). Это одна-две строки в `client/app.ts` у `info`.

### 5.4 GLB павильонов: конвейер и правила

- **Blender без окна** (`-b --factory-startup --python`), экспорт как у фермы (`art/farm/scripts/_lib/farmlib.py:840-849`:
  `export_apply=True`, `export_vertex_color='ACTIVE'`; `export_texcoords=True` — только у сеток семейства `p3_atlas`).
- **Без текстур внутри GLB.** GLTFLoader достаёт встроенные картинки через `blob:`, а CSP игры `img-src 'self' data:`
  без `blob:` (`deploy/game.nginx.conf:12`) — поэтому все 123 GLB игры без текстур, а статуя — свой формат
  (`docs/design.md:2023-2028`). Атлас — отдельный файл `client/assets/plaza3/atlas.webp` через `new URL(…, import.meta.url)`
  и `TextureLoader` (как `client/lobby/statue.ts:32-48`), назначается `p3_atlas` в коде.
- **Без Draco, Meshopt, KTX2**: в CSP нет `'wasm-unsafe-eval'` и `worker-src blob:` — декодеры не запустятся; менять CSP —
  «защита сервера», только по «да» владельца, и не нужно: владелец решил «мегабайты не экономим»
  (`docs/optimization.md:8-9`). Единственное сжатие без WASM — `KHR_mesh_quantization`; инструмента в репо нет, не делаем.
- **Узлы в файле** (`pav_<id>.glb`, один павильон = один файл, корень в начале координат, «лицо» на −Z):
  `static_*` — неподвижное (склеится в квартал), `live_*` — то, что меняется (рамка вывески, вращающийся флюгер,
  дверь), `anchor_*` — пустышки (место вывески, жителя, начала/конца гирлянды, лампочек), `col_*` — боксы
  столкновений **не для клиента**: скрипт выгрузки пишет их в `layout.json` (`colliders[]`) уже в мировых координатах.
- **Загрузка**: все GLB площади параллельно при старте (кэш браузера, файлы с хешем), сначала квартал у точки появления;
  ошибка файла — серый «блокаут» из `colliders[]` вместо павильона (по образцу `loadModel` фермы, который возвращает
  пустую модель, `client/farm/models.ts:64-77`), игра не падает. Склейка — `StaticBatch` по кварталу и семейству.
- **Треугольники**: павильон 3–12 тыс. × ~22 входа ≈ 150–250 тыс., жители 15 × 4–8 тыс. ≈ 100 тыс., предметы —
  инстансами; площадь целиком ≤ 1,2 млн вместе с режимами.

### 5.5 Вывески: одна система, атлас и живой статус

- Вывеска = иконка + название (Rubik 900) + строка статуса ниже; столбы-указатели на развилках — стрелки с названиями.
  Цвета и шрифты — в одном `client/lobby/plaza3/signstyle.ts` (временная палитра из брифа: крем `#fff3de`, чернила
  `#2a1f24`, золото `#ffd35a`, терракота `#d9643a`), чтобы скин из UI-треда (A/B/C) подставлялся одной правкой.
- **Атлас заголовков** 2048×2048 `CanvasTexture`: рисуется один раз после шрифтов (`waitForFonts`, `client/startup.ts`).
- **Атлас статусов** 1024×1024 (строки 512×64): перерисовывается **только при смене текста** и не чаще 2 раз в секунду;
  загрузка — `needsUpdate` всего маленького атласа (4 МБ) или, если замер покажет рывок, `renderer.copyTextureToTexture`
  одной строки из рабочего холста 512×64.
- Геометрия: каждая вывеска — 2 прямоугольника с UV в атласы; все вывески площади — **один меш на атлас** (2 отрисовки),
  `MeshBasicMaterial`, `toneMapped: false` (цвета как в UI), зазор от стены ≥1,5 см или `polygonOffset` (AGENTS §7).
  Дальше 60 м прячутся в вершинном шейдере (масштаб → 0), без работы процессора.
- Источник строк — уже готовые чистые функции `fillLive/liveLines/agendaRows` (PL/`live.ts`, тест `plaza2.test.ts:48-206`);
  новые статусы (бильярд, карты, аркада, сезон рыбалки, лодки) — в новом `client/lobby/plaza3/status.ts`.
  Статусы клиент и так получает — новых сообщений не нужно.

### 5.6 Жители: GLB с жёсткими частями и дешёвое ожидание

- **Модель**: 4 узла — `body` (голова, лицо, одежда — одна сетка, цвет в вершинах), `hand.L`, `hand.R` (точка поворота —
  в плече/запястье), `prop` (мегафон, удочка, поднос; родитель — `hand.R` или свой узел); по желанию `lid` (веко для
  моргания масштабом). 4–8 тыс. треугольников, одно семейство материала. Клипы в файле не обязательны.
- **Рекомендуемая сборка — все жители одной сеткой**: при загрузке части каждого жителя складываются в одну геометрию
  с «жёстким скином» (`skinIndex` = кость части, вес 1), кости = 4–5 на жителя (~70 на площадь, `Skeleton` с
  костной текстурой) → **1 отрисовка на всех**. Ожидание считается в JS раз в кадр для ближних (<30 м) и 8 раз в секунду
  для дальних: покачивание тела, вдох, взмах рукой при подходе, жест с предметом, моргание. Дальше 46 м кость тела
  масштабируется в 0 (житель исчезает без смены материала). Образцы в репо: жёсткие части на костях с инстансами
  (`client/lobby/piratejelly.ts`, `piratecrowd.ts`, `client/fort/mobs/*`), запечённые клипы частей в текстуре
  (`client/dungeon/mobs.ts:67-231`).
- **Запасной путь** (если «одна сетка» не успевается): у каждого жителя тело склеено, 3 мелкие части отдельно →
  4 отрисовки × ~8 видимых ≈ 32; узлы крутит `AnimationMixer` по клипам файла, как Игнат (`client/lobby/isle/island3d.ts:132-201`).
- Тени — пятном под ногами (один инстанс-меш), в статическую карту теней жители не попадают.
- Поведение — как у зазывал (PL/`touts.ts`: прячутся дальше 46 м, поворачиваются ближе 9 м, машут ближе 6,5 м раз в 22 с,
  говорят ближе 15 м раз в 9–13 с живым статусом). Облачка реплик — пул из 2–3 спрайтов, а не у каждого свой.

### 5.7 Видимость по кварталам

- Отсечение по кадру — штатное three.js на каждый склеенный меш квартала (компактная сфера — отсекается целиком).
- Дальность: мелочь квартала (инстансы, гирлянды, таблички) — `visible = false`, если камера дальше 55–60 м от рамки
  квартала (проверка раз в 0,25 с). Скрывать **сетки** `visible` можно — программы пересобирают только лампы.
- Режимы — их собственные правила «обновлять только рядом» (`docs/optimization.md:124`).
- Тени: одна статическая карта на сушу + пирс (сейчас 2048 и рамка 62×92 м, WD:291-296, а look v2 ставит свою
  62×74 м — `client/lobby/look.ts:54-55`). Для 100×75 м суши + пирса: 4096 на «высоком», 2048 на остальных (тот же тип теней — меняется только размер);
  тени под павильонами можно запечь в цвет вершин в Blender.

## 7. Что нужно знать левел-дизайнеру

### 7.1 Главное: береговые линии не двигать, сушу растить на север и восток

Сейчас настил — x −30…30, z −26…22 (LB:214). Берег — прямой угол: **западная кромка x = −30** (аквапарк, гидроплан,
кнехты) и **южная кромка z = 22** (мостки к маяку x −21…−17, катер x ≈ 8, понтон крыс x −10,8…−4, регата у стенки).
Всё к северу от z = 22 и к востоку от x = −30 **уже считается сушей во всех системах**: город и улица
(WD:99-107), физика своих лодок (`ownboat.ts:389-407` — «суша = x > −30,5 и z < 21,8» до x = 2000), молнии
(`weather.ts:180`), рельеф под гидропланом (`plane.ts:132-136`). Поэтому:

- **Растить сушу в четверть «x ≥ −30, z ≤ 22» — бесплатно** для моря: лодки, паром, баркас, катер, кракен, русалка,
  молнии, места ловли, маяк, остров, трасса регаты остаются как есть (§3 — всё «0»). Меняются только рамки города и
  площади в WD и `plane.ts` (через `pick()`, дёшево). Пример: суша x −30…+60, z −58…22 (90×80 м ≈ 2,5 × нынешней).
- **Сдвигать кромки или выходить сушей в море — дорого (Р)**: ручные копии берега в `ownboat`, `weather`, `plane`,
  у зверей (бухта), у пиратов (`PIRATE_WATER_Z` `pirates.ts:279`), у шторма, плюс рассчитанные под берег маршруты
  катера и парома. Широкие лестницы к воде (концепт v2) — только как отделка в полосе ≤ 1,5 м от кромки; валуны
  волнореза у маяка (v3) — декор без столкновений или с правкой `ownboat` `CIRCLES` (`:410-416`, по 1 строке на валун).
- **Маяк, мостки, пирс к дому Семёна и голова пирса** (до z ≈ 64, `FISH_PIER_HEAD`) — стоят. Вокруг них можно
  переставлять только то, что на суше (доски рыбаков, пьедестал, хижину-декор).

### 7.2 Центр и расстояния

- «5–6 с бега» при 8,4 м/с = **42–50 м пути**, не по прямой. Ориентир: по прямой от центра до входа ≤ 40–42 м.
- При неподвижном береге **центральная площадь должна стоять ближе к морскому углу**, а не в геометрическом центре
  суши. Пример: центр ≈ (8; −8) → аквапарк (−30; 9) — 42 м, корень пирса (−19; 22) — 40 м, «Стриж» (−29; −11) — 37 м,
  катер (8; 23) — 31 м. При центре в середине 90×80 (≈ (15; −18)) аквапарк и корень пирса уходят за 52 м.
- Дальние углы суши (северо-восток) — под город, кафе с террасой, кипарисы, дорогу на ферму, а не под входы.
- `check.mjs` (§1.3) считает расстояние по прямой; путь вокруг павильонов левел-дизайнер проверяет глазом на плане.

### 7.3 Какие группы двигать дёшево, какие дорого

| Цена | Что |
|---|---|
| **0 — оставить** | всё на воде и у кромки: маяк и мостки, места ловли 0–27, Семён, «Удалая», свои лодки, баркас, остров, трасса регаты, «Ласточка» с причалом, «Стриж», понтон крысиных бегов, аквапарк «Волна» |
| **Н — новая точка, дёшево** | входы арен (пейнтбол, картинг, крепость, «Выше облаков»: точка + круг старта + спавн возврата), кафе и афиша, примерочная, доска почёта, табло гонки, батуты, скамейки/кадки/фонари, точка появления и дом мяча, **карточные столы (любой список из 3 столов со стульями вокруг)**, вывески, жители, аркада, калитка фермы (`plazaGate` — новый якорь, `yaw` кратно 90°) |
| **С — сдвиг группы, дёшево-средне** | бильярд (зал целиком), ряд автоматов, музыкальный автомат, «Рыбный двор» (прятки), круг регаты + лодки у стенки + мачты, «Рекорды рыбаков» и пьедестал, скала «Подземелья» с доской, колесо обозрения (за ним уедет надпись TIREDWOOD на холме — она стоит по азимуту от `WHEEL`, `plane.ts:149-150`) |
| **П — поворот группы, дорого** | ряд автоматов (`MACHINE_XS` + одно число `MACHINE_FRONT_Z`), бильярд (`blSpot` ±π/2), колесо, аквапарк (`AQUA_NEAR_X`) — **не поворачивать**; средне: музыкальный автомат (`JUKE_USE` считает «лицом на юг»), примерочная (`WARDROBE_OFFSETS` по z), «Подземелье» (3 бокса скалы) |
| **Р — переделать данные** | любые сдвиги береговых линий и маяка; **пираты и шторм** (новая полоса и причалы — нужны в любом случае); маршруты зверей и облёт меню (в любом случае) |

### 7.4 Правила геометрии

- **Столкновения — только боксы по осям** (AABB). Павильоны можно ставить под любым углом визуально, но их твёрдое —
  набор осевых боксов (`col_*` в Blender → `colliders[]`). Проще и надёжнее — павильоны и сборки по осям или на 90°.
- Игрок — бокс 0,84 × 1,6 м (`PLAYER_HALF = 0,42`, `shared/constants.ts:16`); **проход ≥ 2 м**, дверной проём ≥ 1,4 м.
  Ступень ≤ 0,52 м (`STEP_HEIGHT`) — выше уже прыжок; лестницы и террасы — ступени ≤ 0,5 м или пандус.
- **Точка входа (E)** — на настиле, не в стене, игрок должен встать в `r + 0,5` от неё с `|dy| < 2` (сервер, RM:923-932).
  Обычный `r` — 1,4–2,6 м; у сидений 0,7. Перед точкой — свободный пятачок ≥ 2×2 м.
- **Круги старта** (пейнтбол, картинг, крепость, «Выше облаков», прятки, регата) — радиус 3–4 м, внутри без
  препятствий, вмещают 8 игроков (тест `plaza2.test.ts:248-258`). Рядом — место под экран/табло и спавн возврата
  (игрок появляется у входа, из которого ушёл, — RM:652).
- **Пустышки `retired`**: №45 (бывший Fight Club) и всё, что выпадет в будущем, ставь в свободный угол настила, r = 0.
- **Памятник не трогать**: место (−23,6; 19,2) у корня мостков оставить свободным настилом, ничего шумного рядом
  (AGENTS §11; `STATUE` не правим, сервер проверяет «F» по этой точке даже скрытой, RM:1534).
- **Полоса пиратов**: вдоль южной кромки нужен променад глубиной ≥ 8–10 м без плотной мебели — туда высаживаются
  шлюпки и бегут пираты (сейчас `PIRATE_ZONE` x −7…27, z 12,5…22). Скамейки на нём нужны — пираты на них садятся.
- **Новые точки** — только в конец списка (№113+); номера 0–112 не меняются ни при какой раскладке (§1.5).
- **Высоты**: снимок держит y в ±128 м; настил — y = 0, террасы — до +3…4 м, без «вторых этажей» над входами.
- **Рамка теней**: суша + пирс в одном прямоугольнике ≤ ~125 м (с пирсом до z = 64 и севером z −58 это 90 × 122 м) —
  4096 текселей дают ≈ 3 см на тексель.
- **Скаляры дороги**: если константа задана одним числом (`MACHINE_FRONT_Z`, `TABLE_X`, `BENCH_Z`, `AQUA_NEAR_X`,
  `BOAT_DOCK_Z`), группа должна остаться рядом вдоль той же оси — двигай её целиком, не разворачивай.
- **Выезд на ферму** — на суше, к северу/востоку (туда же «город»), вне 50-метрового круга можно, но арка «Огороды»
  должна быть видна с центральной площади; зона «прошёл — на ферму» — прямоугольник на грунтовке за аркой.
